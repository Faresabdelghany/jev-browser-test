# Troubleshooting

Read the row that matches the symptom; every fix is either in the spec, in the environment or a real finding about
the app. `$SKILL` is the skill directory. Exit 2 is never a verdict: fix it first.

| Symptom | Cause / fix |
|---|---|
| The control Jev needs is on screen but never in the element table, and the summary ends with `hint: ... <iframe>` (`reason.hints` in `result.json`; suggested `test_issue` when Jev said `control_not_on_page`) | It is inside an iframe. List the frame's CSS selector in `observation.frames` (its controls then join the table, marked `in "frame: ..."`), or script the step in `setup` with `"frame"` |
| The same, with `hint: ... shadow DOM` | The control is inside a web component and the spec turned shadow DOM off. Remove `"shadow_dom": false` (it is on by default since 0.6.0) and it is observed like the rest of the page; or script the step in `setup`: Playwright selectors reach into open shadow roots (`my-widget button`) |
| With `--reuse-sessions` (or a suite's `--sessions`) a spec still logs in every time | It has no `login` block (its login is in `setup`, where the runner cannot tell it from the rest: move those steps to `login`), its `login` differs from the other specs' by a selector or a value (another key, another session: `result.session.not_reused` says "no saved session yet"), or the application ends the session between runs (`expired: true`: a spec that logs out, or a short server-side timeout) |
| With `settle: "network"`, steps end `settle.ended: "cap"` with `network.left` | A request the action started never finishes within `settle_ms` (a stream, a long poll opened by the click, a slow API). The run is no slower than without the option, but gains nothing on that step. If it is a stream, nothing to do; if it is the API the next page needs, the cap is doing its job |
| With `batch_fields`, a form is still filled one request per field (`BATCH-ENDED`, `result.batch.stopped`) | The page reacts to typing (the reason says how: a validation line, a suggestion list, a field that appears), so the runner stopped and asked, which is the safe reading. Or Jev was not sure which value goes where (`step.fill` has every answer, `thresholds.batch_confidence` the bar): name the data keys like the form's labels |
| A `--replay` run asked Jev on every step (`replay: no saved step used (...)`) | The reason is in the line: no passing run has saved a path yet, the spec was edited since (any edit drops the path), or the run's options differ (device, shadow DOM, frames). The run records a new path when it passes |
| A `--replay` run stopped replaying part-way (`REPLAY-ENDED`, `result.replay.handed_back`) | The page no longer fits the saved step; `reason` says what: a button renamed, a field added, another page, a control gone or now ambiguous. Jev took the run from there. If it passed, the path was rewritten and the next run replays in full; if the reason names a change nobody made on purpose, that is a finding |
| A `--replay` run ended red and the result says `run it once more with --no-replay` | Do that before judging (a suite with `--replay` already did, and shows the second run). The same red without the path is the application's; a pass without it means the path no longer fits the page's timing or state: the passing run rewrote it, and if it happens again, raise `browser.settle_ms`, or keep that spec out of replay with `"replay": "never"` (it beats `--replay`) |
| A click opened a new tab and the run stalled on the old page (`NEW-TAB(not followed)`) | Set `browser.follow_new_tabs: true`: the run then carries on in the tab the click opened |
| The flow needs a file upload | Declare `"files": {"cv": "path/to/cv.pdf"}` and name the upload in the goal: Jev chooses `UPLOAD_FILE`, the field and the file (hidden file fields included). Or script it: `upload {selector, path}` in `setup` |
| The flow needs a menu that opens on hover | `"extra_operations": ["HOVER"]` and a goal that says so ("hover Products, then choose Pricing"). Or script it: `hover {selector}` then `click` in `setup` |
| The flow needs a drag | Scripted only: `drag {selector, to}` in `setup` |
| With `HOVER` offered, Jev hovers where a click was due (or decisions on unrelated steps got less certain) | The cost of an extra operation. Take `HOVER` out of `extra_operations` and script the one hover in `setup`; `scripts/ab.py <spec> --b-arg=--hover --repeat 5` measures it |
| `UPLOAD_FILE` flagged `NO-EFFECT`, or the file is attached twice | The page shows nothing when a file is chosen. The field reads `(file: name)` in the next step's table; say in the goal what follows the upload ("attach the CV, then click Submit") |
| A spec that passed for weeks goes red on one calendar day and stays red (a record 'not found', a status that reads Taken or Expired, 'date must be in the future') | A literal date in `data` has passed. Write it as `${DATE+2d+workday:<the app's format>}` (and the same placeholder wherever the goal, notes or assertions name the day); `RUN_DATE=yyyy-mm-dd` reruns the spec as of another day |
| A date placeholder's run is refused on some days only ('No Working Days Selected', 'closed on this day') | The day it names is a weekend or a holiday there: use `+workday` and copy the application's holidays into `calendar.holidays` (`"12-25"`, or `"2026-12-28"` for one year), its work week into `calendar.workweek` if it is not Monday to Friday |
| A run leaves records behind and the next run trips over them | `${RUN_STAMP}` in the data keeps runs apart; a `teardown` block deletes what the run created, after the verdict and whatever it was |
| `JS-ERROR`, `HTTP-5xx` or `REQ-FAILED` on the step after an action | The browser's own report of what the action caused: `result.diagnostics` has the exception or the request. Evidence for the ticket, and the difference between a dead control and a failing backend; add `{"no_page_errors": true}` / `{"no_failed_requests": true}` to `assert` to make a clean console and network part of the pass |
| exit 2 with `unknown browser.device` | The name is not in Playwright's device list; the message names the closest ones (`iPhone 13`, `Pixel 7`, `iPad Mini`) |
| `TYPESAFE_API_KEY is not set` | Export the key or put it in `.env` in the directory you run from |
| No window appears, or one appears unannounced | The launch line says which mode ran: `browser: headed` or `browser: headless (...)`. Precedence: `--headed` / `--headless`, then `JEV_HEADED` in `.env`, then the spec's `browser.headless` (default true). A window no run announced belongs to another tool's browser, not to this runner |
| exit 2 with "Spec problems" | Read the list: a `done_when` naming an unknown check, a check written as a question, a missing `${ENV}`, an `assert` of the wrong shape |
| exit 2, `reason.phase: navigation` (`Page.goto: Timeout`) | The start URL did not load within `browser.navigation_timeout_ms` (30 s): a slow or unreachable host, or too many parallel workers on a shared one. Environment, never a bug: rerun sequentially, raise the timeout |
| exit 2, `reason.phase: setup` (`setup[i] failed`) | The selector or `wait_for` in a setup step did not match; fix it or move that step into the goal |
| `blocked` right after a text field appears (`blocked_reason: missing_data_value`) | Add the needed value to `data` |
| `blocked` / `stuck` after a click flagged `NO-EFFECT` (`stuck_reason: control_had_no_effect`, suggested BUG) | A dead control, the classic product bug. The next step's picture shows the unchanged page; confirm the click landed on the right control in `--step N` |
| A bug outcome fires at step 1 with zero actions | Its `when` is true of the start page ("the list is still unsorted"). Set `requires_action: true` on it |
| `assert_failed` | A pass was seen but an assertion did not hold: `reason.failed_assertions` has the actual values. Decide whether the assertion or the app is wrong; never loosen it silently. A pass sighted on a page still busy (`COVERED` under a blank layer, an empty document, or changed during the pause) is rechecked twice before this ends, and while it stays busy for as long as `navigation_timeout_ms` (`RECHECK:n ASSERT-PENDING:n`, `recheck_waited_ms` on the parked looks); if the run still ends here with those flags on its last steps, the page took longer than that to settle: raise `navigation_timeout_ms` |
| `done_unverified` with `RECHECK:n` / `COVERED:m` on its last steps | Jev said DONE and the page the pass should show on stayed busy (a record page under its loader) through the confirmation looks, which run for as long as `navigation_timeout_ms` on a busy page. Read `result.reason.assertions_at_last_look`: an assertion that held (the record's URL) plus an `announcements` entry (the save's toast) says the action succeeded and only the confirmation ran out of time. Not a bug: raise `navigation_timeout_ms` / `settle_ms` for that host, or rerun once in a normal hour |
| Every page of a shared demo host takes seconds (`SLOW-NAV`, `COVERED` waited out, `DEFERRED-*`, a late pass) | The host's slow hour, not the runner or the app. Probe before deciding anything: three `curl -s -o /dev/null -w '%{time_total}\n' <login url>`; above ~2 s a page, run on one worker, expect the slow flags, and read a red against them |
| `visible_text` names a control (Save, Submit) that the element table lacks, and Jev clicks something else nearby (an icon, a calendar) | The control sits below the first screen. Form controls and buttons below the fold are offered marked `(below the fold)` and the click scrolls to them; links and plain clickables there are not, so for those say in the goal or `notes` where to scroll ("scroll down to the bottom of the form"): Jev then chooses SCROLL_DOWN (a wheel when the page scrolls inside a container). Or raise `browser.viewport` |
| A click lands on `clickable ""`, an unnamed icon | Icon-only controls are named from their icon class when they have one (`calendar icon`); one still unnamed shows its tag and position in `--step N`. Say in `notes` what the icon does and not to click it, or which named control to use instead |
| A type-ahead answers 'No Records Found' for a value the same page displays | The filter matches less than the displayed text (one name part). Declare it: a `suggestion_not_found` bug outcome with `requires_action` and `after: {type: <the field's label or placeholder>}`, so the run ends declared instead of `low_confidence`; then decide with a control (a sibling filter, the API) whether it is the app's |
| Every command would prompt: `cd <project> && python ...` does not match the skill's pre-approved commands | Change directory once, in its own command (the Bash tool's working directory persists), then start each run command with the interpreter; the runner reads `.env` from the working directory. A pipeline that must keep the exit code needs `set -o pipefail` before `\| tee` |
| `SLOW-NAV:<s>` on a click | The click landed and the page it asked for answered after `action_timeout_ms` (8 s); the runner waited for it within `navigation_timeout_ms` and Jev was told the click worked. A slow host: wall time, not a verdict. Before this was read from Playwright's log the click was recorded as failed and the "failed" clicks in the history dragged every later decision of the run below the confidence gate (five OrangeHRM specs, twelve runs of fifteen `low_confidence` in one slow hour) |
| An assertion on a message passes on every load | `text_contains` searches the whole page and the page's copy mentions the words. Use `text_in` with the element's selector |
| The outcome that came back does not match what the screenshot shows | The spec mislabelled it: fix that outcome's `when` or `verdict`, rerun, say so |
| Two outcomes hover at 0.4–0.5 while the page clearly shows one | Both `when`s are true of that page; reword them with a string unique to each |
| A pass outcome hovers at 0.7–0.85 although the page plainly shows it | The page's copy repeats the same words elsewhere (an example sentence, a menu). Anchor the `when` on the element as well as the text ("the blue bar above the heading reads …"), and put the exact text in a `text_in` assertion |
| A "first item / top of the list" statement reads 0.6 when it is plainly true | Positional facts are soft for Jev; state them in `assert` (`text_in` on the first item's selector, `text_order`) and keep the outcome `when` on what the page says |
| `evidence.line` is null although the outcome is right | The `when` mixes several facts or history in one sentence. One plain page fact per sentence, history in its own sentence; an absence has no line to quote, `evidence.present` is its evidence |
| `low_confidence` with `type_value` split between two keys | Rename `data` keys to the field labels the app shows |
| `low_confidence` over several elements with the same label | The observer names them by their card or row; if the table still shows bare duplicates, say which one in `notes` ("the third Add to cart") or script that click in `setup` |
| `stuck` with confidence ≈ `min_confidence` and flat target probabilities | The control Jev needs is not in the table (a div with no role or cursor hint): a `setup` click or an ARIA role in the app. TEST_ISSUE, note the accessibility gap |
| `budget_exhausted` with `stuck_reason: still_loading` | The page was still loading when the budget ran out. Rerun once; then raise `budget`, or suspect a loader that never completes |
| `unstable_page` | The page never held still (`step.stale` says what moved). Raise `browser.quiet_ms` / `settle_ms` or `wait_for` the thing that keeps changing in `setup` |
| `low_confidence` with WAIT and DONE split around 0.45 while a loader is visible | Jev could not tell "still loading" from "done". Undecided steps already wait like a WAIT (`settle_ms` × 1, 2, 4, ending when the page changes) and the count restarts when the page changes; if the run still ends before the loader does, raise `settle_ms`, and name the loader's end in the goal ("until the message X appears") |
| Jev typed into a search or filter box while a form was still loading (`COVERED:<n>` on that step) | The form's own fields sat under a loading overlay, so the one free field got the text. A marginal action there (below `thresholds.covered_action_confidence`, 0.9) is deferred by the runner while the layer is blank (`DEFERRED-TYPE_TEXT:<n>`, `DEFERRED-CLICK:<n>`: a wait of `settle_ms` × 1, 2, 4, 4, 4, each ending when the overlay lifts or the dialog opens, five on one page, then `DEFER-LIMIT:5` and the action goes); a confident one is executed, so if it still happens add a `notes` sentence naming what to wait for ("type only once First Name and Last Name are shown; the sidebar Search filters the menu"; "wait for the dialog before clicking anything else"); for a start page, `wait_for` the form in `setup`; a loader that outlives the five waits wants a larger `settle_ms` |
| The app confirms or refuses by a toast that is gone before the next step (`Successfully Saved`, `Failed to Submit`) | The runner records toasts and ARIA live messages as they appear (`announcements` on the step and in the result, `ANNOUNCED` flag) and Jev sees them for three observations, so an outcome `when` may name the toast ("A red toast says 'Failed to Submit'") and gets the message as its evidence line. If a spec still misses one, the app's toast has neither a live role nor a toast-like class name: anchor the outcome on the stable state instead |
| Jev clicked Search (or moved on) while an autocomplete still said 'Searching....' | The suggestions were on their way: the runner does not offer such a row, counts it (`LOADING:<n>`) and defers a marginal action while it shows (`DEFERRED-<OP>:loading`, a wait ending when the suggestions arrive); a confident action goes, so if it still happens the `notes` sentence about the placeholder row and choosing the suggestion is the lever, and a larger `settle_ms` gives the list more time before Jev looks |
| A bug outcome fires before the action that gives it meaning (`No Records Found` on an unfiltered list before Search) | `requires` on checks is a probability, not an event. Put `"after": {"click": "Search"}` on the outcome: it is deferred (`DEFERRED:<name>`) until a click on Search has been executed |
| A suite reads `flaky` but every run is a clean declared outcome | The app varies by design; see Suites. A spec with two legitimate pass endings agrees on verdicts, so declare both as `pass` outcomes |
| An expected-red spec keeps a nightly gate red | Declare its ending in `expect`; the suite then reads it `expected` and goes red only when the behaviour changes |
| Choice rejected as too large | Lower `observation.max_elements` |
| Page needs an existing login session | `browser.storage_state`, or attach to a logged-in Chrome (`--cdp-url http://127.0.0.1:9222`); recipe in `references/spec-format.md` |
| Elements inside iframes are missing | Main frame only for now; `references/runner-design.md` says how to extend |
